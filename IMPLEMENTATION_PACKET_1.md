# RAD Local implementation packet 1

## Goal

Build and prove the Stage 1 plumbing foundation for `rad-local-starter`.

This packet is limited to design-independent plumbing. Do not build the final section library, Brickrite retrofit, RAD pilot, n8n automation or demo generator.

## Sources and precedence

1. `docs/internal/RAD-Local-Decisions.md` is binding and wins if sources conflict.
2. `docs/internal/RAD-Local-System-Setup-Guide.md` contains the sequential line-level build specification.
3. `docs/internal/RAD_Local_System_Handover_Brief.txt` is the supplied orientation and sequencing brief.
4. `docs/internal/SOURCE_STATUS.md` records current external gates.
5. The requirements below consolidate the supplied sources and ClickUp Stage 1 task.

Do not invent product or commercial decisions. Record any material ambiguity in `docs/internal/OPEN_DECISIONS.md`.

## Locked architecture

- Astro, TypeScript, static-first.
- Vercel hosting and preview deploys.
- Resend for contact-form delivery.
- One reusable starter repository.
- One per-client `site.ts` as the source of truth.
- One `brand.ts` build-type flag: `direct` or `whitelabel`.
- Default must be `whitelabel`.
- Direct mode alone may render a `powered by Ready Aim Digital` footer attribution.
- White-label rendered output must contain no RAD attribution or references.
- Design tokens in `src/styles/tokens.css` are the re-skin mechanism.
- LocalBusiness schema is generated from `site.ts`.
- Internal methodology, `CLAUDE.md`, README and tooling must not ship in client exports.
- The central `rad-skills` repository is separate from this starter and no skill files may be copied into this repository or a client export.
- Client-editable content must remain cleanly separable from section markup as props or typed data. Do not build a dashboard or runtime CMS in this packet.
- GA4 and GSC are per-client. Direct RAD Local clients use the dedicated standing account documented in the Decisions file. White-label GA4/GSC ownership is deferred and must not be guessed.

## Functional requirements

### Configuration

- `site.ts` must define typed client data sufficient for business name, description, URL, locale, contact details, social links, address, service area, opening hours, images and default SEO.
- Page metadata, canonical URLs, Open Graph data, robots/sitemap host references and LocalBusiness schema must derive from config wherever applicable.
- `brand.ts` must have a typed `buildType` and default to `whitelabel`.
- Avoid duplicated business facts across pages and components.
- Keep future client-editable copy and facts in typed config or page data rather than baking them into reusable component markup.

### SEO plumbing

- `BaseHead.astro` must produce title, description, canonical and Open Graph metadata without Astro generator attribution or RAD references in white-label output.
- `SchemaOrg.astro` must render valid JSON-LD generated by `schema.ts` from `site.ts`.
- Do not put RAD in schema `author`, `sameAs`, comments or defaults for a white-label build.
- Do not encode any internal GA4/GSC account identity into rendered public output.
- Provide robots and sitemap behaviour appropriate to the configured canonical site URL.
- Gate GA4 behind `PUBLIC_GA4_ID`. No analytics script when unset.

### Branding

- Footer renders the powered-by line only in direct mode.
- White-label mode must be clean by construction.
- Internal infrastructure may retain RAD naming only where it is guaranteed never to enter a client export.
- Include automated tests proving the default is white-label, white-label output has no RAD attribution, and direct output has the configured attribution.

### Contact form

- Implement a contact page and Vercel-compatible server endpoint.
- Validate and normalise input on the server.
- Include at minimum name, email, phone and message, with phone optional unless sources require otherwise.
- Include a bot mitigation mechanism that does not require an external paid service for this packet, such as a honeypot and sensible validation.
- Send via Resend using environment variables.
- Do not expose secrets to the browser.
- Use safe error responses without leaking configuration or stack traces.
- Add unit tests around validation and endpoint-level behaviour with Resend mocked.
- `.env.example` must include `RESEND_API_KEY`, `CONTACT_TO_EMAIL`, `PUBLIC_GA4_ID`, and any additional sender variable needed for a correct Resend implementation.

### Pages and UI

Create functional, deliberately minimal placeholder pages:

- Home
- About
- Services
- Contact
- Privacy
- Terms
- 404

Use neutral fictional business content, not RAD or Brickrite content. Legal pages must be clearly marked as templates requiring client-specific review and population before launch.

Create minimal reusable UI primitives needed for this vertical slice, including an attribution-aware Footer. Do not pre-build the final section library.

### Tokens

- Define approximately 12 clear CSS variables covering colour, typography, radius, spacing and container behaviour.
- Ensure the minimal pages actually use the tokens.
- If Tailwind is added, use the current supported integration and map token-based values without duplicating the source of truth.

### Export boundary

- Add `.exportignore` excluding `.git`, `CLAUDE.md`, README, internal docs and internal tooling.
- Do not implement the final Stage 6 archive generator in this packet unless a small helper is required by tests.

### Documentation

- `README.md` must explain local setup, environment variables, build, checks and Vercel deployment.
- `CLAUDE.md` must tell future Claude Code runs how to preserve the one-config pattern, build-type default, white-label cleanliness, token contract and export boundary.
- Internal documentation must live under `docs/internal/` and be excluded from client export.

## Quality requirements

- Use pnpm and commit the lockfile.
- Use strict TypeScript.
- Add Astro typechecking.
- Add unit tests with a maintained test runner.
- Add browser-level smoke tests only if they can run reliably in this environment without bloating the packet. Otherwise document them as the next QA packet.
- No secrets or real client data.
- No dependency with a known high-severity audit issue if a safe maintained alternative exists.
- Use Australian English in sample copy.
- Do not use em dashes in prose.

## Required commands and exit evidence

Before declaring completion, run from a clean working tree state as far as practical:

1. `pnpm install`
2. `pnpm check`
3. `pnpm test`
4. `pnpm build`
5. A search of built white-label output proving it contains no `Ready Aim Digital`, `readyaim.digital`, `built by RAD` or equivalent attribution.

If a command fails, fix it rather than merely documenting the failure.
